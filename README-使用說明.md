# 期刊稿件審查與修訂系統：檔案與使用說明

## 一、檔案一覽

| 檔案 | 用途 |
|---|---|
| `dify/journal-review-loop.yml` | **匯入 Dify 的工作流**（已內嵌所有提示詞、審查標準與程式碼） |
| `tools/web_app.py` | **本機網頁版（自己使用）**：瀏覽器上傳稿件、看進度、下載 Word 報告 |
| `tools/run_review.py` | 命令列版：同樣的功能，也提供 `--from-json` 把已存的結果轉成 Word |
| `review-rubric.md` | 審查標準（8 種論文類型） |
| `journal-manuscript-reviser/SKILL.md` | 修稿者規則 |
| `reviewers/*.md` | 審查 A、審查 B、期刊格式解析、格式整理的提示詞 |
| `dify/code-node-*.py` | 各程式碼節點（已內嵌於 yml，單獨提供供檢視與維修） |
| `dify/build_dify_dsl.py` | 由上述檔案重新產生 yml（修改 md 或 py 後執行一次即可） |

## 二、流程

開始（貼上或上傳稿件、論文類型、期刊格式來源）→ 稿件前處理（清理、保護表格與倫理段落）
→ 期刊規範（內建預設，或解析上傳的期刊格式檔）→ **循環：審查 A、審查 B → 判斷 → 修稿**
→ 格式整理（只改版面）→ 格式整理防護（內容不得被更動）→ 修訂前後句子比對 → **終審意見（Claude）**
→ 產生報告資料（最後一輪修訂標紅）→ 結束

## 三、論文類型（開始表單）

quantitative 量化／qualitative 質性／theoretical 理論與政策分析／teaching_practice 教學實踐／mixed 混合方法／
content_analysis 內容分析／historical 歷史途徑／institutional_comparison 制度比較／cross_cultural 跨文化研究／literature_linguistics 文學與語言研究

## 四、匯入後要做的事

1. 重選 6 個 LLM 節點的模型：審查 A、審查 B、Claude 修稿、期刊格式解析、格式整理、終審意見（格式解析與格式整理用低成本模型即可）。
2. 確認環境變數 `DEFAULT_FORMAT_RULES`（內建預設格式）符合你的習慣，可直接修改。
3. 發佈工作流（使用 `run_review.py` 時需要）。

## 五、正式使用：本機網頁版（自己使用）

1. `pip install requests python-docx`
2. 在 Dify 發佈工作流，「訪問 API」取得網址與金鑰；在 `tools/` 資料夾建立 `.env` 檔，兩行：
   `DIFY_BASE_URL=https://你的dify網址/v1` 與 `DIFY_API_KEY=app-xxxx`
3. `python tools/web_app.py`，瀏覽器開啟 http://127.0.0.1:8000
4. 上傳稿件（可選期刊格式檔）→ 開始 → 完成後下載 Word 報告。

只綁定本機（127.0.0.1），金鑰不會顯示在網頁上；所有檔案存在 `tools/runs/`，其中含未發表稿件，請自行管理。

## 六、其他取得 Word 報告的方式

- 命令列：`python tools/run_review.py 稿件.docx --type historical --format-file 稿約.pdf`
- 已在 Dify 網頁跑完：把結束節點的 `report_json` 存成 `outputs.json`，執行 `python tools/run_review.py --from-json outputs.json`
- 結束節點的 `report_html` 可存成 `.html`，用 Word 開啟。
- Google 文件：把 `.docx` 上傳到 Google 雲端硬碟，以 Google 文件開啟。

## 七、計分與審查者分工

- 審查 A（方法與論證）主責 A、C、D、E、F；審查 B（文獻與格式）主責 B、G。綜合分數以主責審查者為主（75%）。
- **面向分數上限**：任一面向只要有未解決的 major 意見（不論誰提出），該面向綜合分數上限 3.5；有 critical 則上限 2.5。
- 只有「一位判 reject、另一位判 accept 或 minor」才會停下交人工裁決；面向分差過大僅在紀錄中提示。

## 八、作者已知待補事項（開始表單選填）

列出你打算自行處理的缺口（例如「質性分析程序細節」「補充實證文獻」）。審查者仍會提出這些問題，但**嚴重度最高為 minor**，
問題文字以「【已知待補】（原嚴重度：major）」開頭，**不會阻擋通過**；修稿者不會嘗試處理它們，只維持稿中的【待作者補充】標記。
這是為了讓「只剩需要作者補事實的問題」時，系統仍有機會判定通過。**清單以外的問題不受影響，照常把關。**

## 九、修稿者規則重點（SKILL）

不編造事實、不改數據與鎖定區塊；不替既有文獻添加論點；不新增方法或程序描述；不替作者陳述動機或理據；
給作者的提示只能寫在【待作者補充／確認】標記內，不得寫成正文句子；史料、信度、條文等領域性事實一律照原稿。

## 十、終審意見與審計基準

終審意見由 Claude 擔任，**比對基準是你上傳的原稿（累計所有輪次的修改）**，不是最後一輪的前一版。
報告中的**紅字**則只標示最後一輪修訂。兩者基準不同是刻意的：紅字讓你看最後一輪改了什麼，審計則確保任何一輪新增的內容都被檢查。

終審判斷標準：可投稿＝沒有未解決的 major 且沒有未標示的新增內容；修正後可投稿＝剩餘問題為 minor、已標示待補或作者已知待補，或只需作者補事實；
需重大修改＝需要改寫論證或研究設計才能解決的 critical 或多個 major。

## 十一、已知限制

- 審查者是否把問題標示為「已知待補」依賴模型判斷；逐輪紀錄會顯示「你填了 N 項、審查者標示了 M 項」，M 為 0 時請檢查清單用語。
- 終審與修稿者都可能漏掉未標示的新增陳述，**定稿前仍需你逐句核對標紅與新增處**。
- 參考文獻只經過稿內一致性檢查，不代表真實存在。

## 十二、下載「依期刊格式調整後」的稿件（Word／.doc／PDF／Google 文件）

流程的結束節點新增輸出 **`layout_spec`**（版面規格 JSON）。來源有兩種：
- 開始表單選「**上傳期刊格式檔**」：解析節點會從稿約整理出版面規格（頁面邊界、中英文字型、字級、行距、首行縮排、標題、表格樣式、表題位置、書目懸掛縮排、頁碼）。**稿約沒寫明的項目一律採內建預設，並列在 `unspecified` 中**，不會憑空補寫。
- 選「內建預設格式」：標楷體／Times New Roman、12 pt、1.5 倍行高、A4、上下 2.54 cm、左右 3.17 cm、頁碼置中。

**方法一（本機網頁版，最省事）**：`python tools/web_app.py` → 上傳稿件 → 完成後點「下載修訂稿 Word（依期刊格式）」，同時提供 .doc 與 PDF（需安裝 LibreOffice，沒安裝會自動略過）。

**方法二（只用 Dify 測試頁面）**：把「結果」頁的輸出 JSON 存成 `result.json`，然後執行
```
python tools/export_docx.py result.json -o 修訂稿.docx
python tools/export_docx.py result.json -o 修訂稿.docx --also-doc --also-pdf
```
需要 `pip install python-docx`。

**Google 文件**：把 .docx 上傳到 Google 雲端硬碟 → 對檔案按右鍵 → 開啟方式 → Google 文件。

**注意**
- 預設會保留【待作者補充／確認】標記並以**黃底**標示，避免未處理的缺口被悄悄帶進投稿稿；定稿時請逐項處理後再移除。確定要移除可加 `--strip-markers`。
- 版面只由程式套用，**不經過模型改寫文字**，因此不會改動內容。
- 稿件中以 `<!--LOCK-->` 保護的表格會轉成 Word 表格（格線或三線表，依稿約）。
- 參考文獻的排序若由模型處理，請人工核對（尤其中文筆畫）。

## 文獻背景檢索（Google Scholar via SerpApi）
- Google Scholar 沒有官方 API，直接爬取會被封鎖且違反條款；本流程改用 SerpApi 的 google_scholar 引擎。
- 在 Dify 環境變數填入 `SERPAPI_KEY` 即啟用；留空則自動略過，其他流程照常。
- 流程：產生三組查詢（LLM）→ 三次檢索 → 整理成清單 → 餵給兩位審查者。清單只供評估「文獻定位與缺口」，意見最高 minor，不得憑記憶補書目。
- 輸出新增 `literature_report`（檢索摘要）與 `literature_context`（給審查者的原文）。

## 新增：跨文化、文學與語言研究類型，及文獻清單強制使用（2026-10-10）

- 論文類型新增 `cross_cultural`（跨文化研究：文化概念界定、概念／測量／樣本／語言等值、翻譯程序、詮釋位置性、替代解釋）與 `literature_linguistics`（文學與語言研究：論點與文本證據、版本與語料、理論架構、引文與譯文處理、語言分析方法；語言學實證研究另適用量化／內容分析項目）。標準見 review-rubric.md 類型 9、10；權重已加入程式。
- 修稿者新增鐵則 8b：原文引文、外語原文、譯文、語料例句、頁碼版本，以及翻譯／等值檢驗／標註程序，一律不得改寫或補寫。
- 兩位審查者現在必須輸出 `literature_use`（列出文獻清單中相關的項目、稿件是否已處理）；清單中直接相關卻未處理的研究，審查者須在面向 B 提 minor 意見；研究缺口可能已被處理者，在面向 A 提 minor 意見。程式會核對編號與標題是否真在清單內，並把結果寫入審查紀錄（「文獻清單使用：採計 N 筆，稿件未處理：…」）。
- 文獻檢索字串會依論文類型調整（跨文化、文學與語言有專屬提示）。
- 重新匯入 yml 後，請再填一次 `SERPAPI_KEY`，並確認 Claude 節點的 Adaptive Thinking 為關閉。

## 對齊診斷節點（計畫書預審；v1.1 新增）

- 位置：文獻背景檢索之後、審查迴圈之前，只在 `paper_type = teaching_practice_proposal` 時執行一次（期刊稿件自動略過，不增加成本）。
- 作用：抽取稿中的「理論清單」與「計畫項次清單」，建立「研究問題 × 理論／活動／工具／分析／成果」對齊矩陣，列出孤兒項（掛名理論、無學理依據的活動、無資料可回答的研究問題）與核心理論的論述深度，並給作者「待補方向」。
- 接法：診斷結果附在審查者與修稿者讀取的 `extra_context` 結尾，不改動迴圈本身；輸出新增 `alignment_report`、`alignment_status`。
- 分工：Dify 只診斷、不補寫；缺口一律標【待作者補充】，由作者或 Claude Project 依診斷改寫。
- 提示檔：`proposal/reviewers/alignment-diagnosis.md`；合併程式：`dify/code-node-12-align-merge.py`；審查標準補充規則 10 說明審查者如何使用診斷報告。

## v1.3：差異式修稿與文獻檢索調整

- **修稿改為差異編輯**：修稿者在自動化模式只輸出 `<edits>` 修改清單（replace／insert_after／insert_before／delete，逐字引用原句），由「⑦ 解析修訂」程式節點套用到當前稿件，再產生完整修訂稿。輸出量縮減為原本的約 1/5 至 1/8，不再有「輸出被截斷」；原句找不到、不唯一、重疊、碰到 LOCK 區塊的修改會被略過並在報告列出，對應意見的處理狀況自動降為「需人工處理」。舊格式（`<revised_manuscript>` 全文）仍可解析，必要時把 `REVISER_SKILL` 換回舊提示即可退回。修稿節點的 Max Tokens 由 48000 調為 16000。
- **文獻檢索**：查詢產生提示加入孫子兵法、認知作戰、媒體識讀、軍事教育、兩岸關係等主題的中英用語對照與避免泛化詞的規則；計畫書的檢索用開頭改從「計畫執行內容／研究動機」起算，不再取封面與主持人資料。
